# SOTA digest — 2026-W30

_Swept 2026-07-22 (UTC). Window: roughly 2026-07-12 → 2026-07-22._

## Bottom line

The week's real news is that **pattern-based command allowlists are now a
documented, named failure class** — GuardFall broke them in 10 of 11
open-source coding agents, and OWASP's 2026 report describes a Cursor CVE
where the allowlist *helped* the attacker by auto-approving what they needed.
This toolkit ships a 141-rule permission baseline to every machine, so that
finding lands squarely on `claude/settings.json`. Everything else was
incremental: Claude Code shipped a fortnight of permission-checker hardening
in the same class, plus runaway caps for background subagents, and the MCP
stateless spec finalises on 2026-07-28.

## What moved

### 1. Agent CLIs and coding harnesses

- **Claude Code v2.1.208 → v2.1.218** (Jul 14–22) is dominated by
  permission-checker hardening that maps 1:1 onto the GuardFall bypass
  classes: Bash checks now fail closed on file-descriptor redirect forms,
  commands over 10,000 characters always prompt, zsh subscripts inside
  `[[ ]]` no longer count as inert text, non-ASCII parsing was changed to
  match real shell word boundaries, and compound statements with redirects
  inside `&&` lists are checked correctly. Anthropic is independently
  patching the same guard-vs-shell mismatch GuardFall names.
  <https://code.claude.com/docs/en/changelog>
- **Runaway caps for unattended runs** (v2.1.212, v2.1.217): per-session caps
  on subagent spawns (200) and WebSearch calls (200); a concurrency cap on
  subagents (default 20, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`); subagents no
  longer spawn nested subagents by default; and `--max-budget-usd` now
  actually halts running background subagents instead of only denying new
  ones. Directly relevant to `vibe loop`, which today bounds a run by rounds
  (`--max`) and wall-clock (`--for`) but not by spend.
  <https://code.claude.com/docs/en/changelog>
- **The vendor moved toward this repo's SQ13 convention.** v2.1.215 stopped
  Claude from invoking `/verify` and `/code-review` on its own; v2.1.218 did
  the same for `/deep-research`. That is the same reasoning behind
  `disable-model-invocation: true` on the nine side-effecting skills here —
  no action, but the convention is now vendor-endorsed rather than local
  taste. <https://code.claude.com/docs/en/changelog>
- **New skill frontmatter surface** (v2.1.218): skills with `context: fork`
  run in the background by default (`background: false` opts out), and
  frontmatter booleans now accept `yes`/`no`/`on`/`off`/`1`/`0`. Noted, not
  adopted — `context: fork` is Claude-specific and `skills/` is the portable
  half of the layout contract.
  <https://code.claude.com/docs/en/changelog>

### 2. Protocol and ecosystem

- **MCP 2026-07-28 ships in six days.** The release candidate drops the
  `initialize` handshake and `Mcp-Session-Id` entirely (stateless core),
  adds an Extensions framework with reverse-DNS IDs, graduates Tasks to an
  extension, adds MCP Apps (server-rendered UI in sandboxed iframes),
  hardens authorization toward OAuth 2.0/OIDC, and puts Roots, Sampling and
  Logging into a formal 12-month deprecation window.
  <https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/>
  This is *not* a recommendation — `PROJECT_ROADMAP.md` Track B already holds
  "curated MCP server list in `docs/`". It is a timing note for whoever picks
  that item up: written before 2026-07-28 the doc would describe a protocol
  with a twelve-month deprecation clock on three of its features.

### 3. Security

- **GuardFall** — five bypass classes (quote removal `r''m`, `$IFS` field
  splitting, command substitution computing the binary name, base64 piped to
  a shell, alternative argv shapes) defeat pattern-based command guards
  because the guard reads raw text while bash expands, unquotes and rewrites
  before executing. 10 of 11 surveyed open-source agents were vulnerable;
  only `continuedev/continue`, which tokenizes and canonicalizes before
  matching, was not. Claude Code was **not** in the survey.
  <https://adversa.ai/blog/opensource-ai-coding-agents-shell-injection-vulnerability/>
- **OWASP 2026 / CVE-2026-22708 (Cursor)** — the sharper framing of the same
  problem: "the allowlist made the attack easier by auto-approving the very
  commands the attacker needed." Prompt injection maps to six of the ten
  OWASP Top 10 for Agentic Applications.
  <https://www.helpnetsecurity.com/2026/06/11/owasp-prompt-injection-ai-security-failures/>
- **Claude Code GitHub Action supply chain (CVE, CVSS 7.8)** — a malicious
  GitHub App creates an issue, prompt injection makes the agent read
  `/proc/self/environ`, the leaked OIDC request token is exchanged for a full
  installation token. Fixed in action v1.0.94; disclosed 2026-06-01.
  <https://flatt.tech/research/posts/poisoning-claude-code-one-github-issue-to-break-the-supply-chain/>
  **Checked and not applicable here:** `.github/workflows/ci.yml` and all
  five `templates/ci/*.yml` use only `actions/checkout`, `actions/setup-*`,
  `astral-sh/setup-uv` and `dtolnay/rust-toolchain`. No Claude action is
  referenced or emitted by this repo.
- **PhantomSkill / VulMask** — hides malicious behaviour in a skill's
  auxiliary resource files by shaping it like vulnerable-looking code, which
  evades skill scanners and automated reviewers. Relevant to what
  `security-sweep` is asked to catch when vetting third-party skills.
  Reported via the July roundup; the arXiv primary
  (<https://arxiv.org/abs/2606.19191>) was not fetched this round.
  <https://adversa.ai/blog/top-ai-coding-agent-security-resources-july-2026/>

### 4. Practice

- Practitioner consensus on unattended loops converged on four things a loop
  must state: the desired end state, the evidence required, the constraints
  that must hold, and **a hard budget** — "without a hard gate, loops fail
  quietly and keep spending." `LOOP.md` covers the first three (goal, stop
  check, constraints) and `--max`/`--for` bound rounds and time; spend is the
  gap. A 2026 study also reports gains from isolating each agent in its own
  git worktree and verifying, which is the `vibe` model already.
  <https://www.requesty.ai/blog/loop-engineering-how-to-build-ai-agent-loops-that-run-themselves>

## Recommendations

### 1. Re-frame the permission baseline as defence-in-depth, not a guard

**Goal:** `claude/settings.json`'s `deny` array and `CLAUDE.md`'s permission
section state plainly that pattern rules are advisory against an adversary,
name the canonical control that actually holds for each thing being
protected, and close the gap where no canonical control exists.

Design:

- The ten `Bash(git push * --force …)` deny patterns are exactly the class
  GuardFall breaks: `git push --f'o'rce`, `git push --force$IFS`, or a
  base64-piped equivalent all read as different raw text and execute the
  same. Do **not** try to enumerate the bypasses — the research's own
  conclusion is that raw-text matching cannot win; only
  tokenize-and-canonicalize does, and that is the harness's job, not a
  settings file's.
- The canonical control that *does* hold is `.githooks/pre-push`: it reads
  git's ref protocol line-by-line, after every shell expansion, so it refuses
  any push to `refs/heads/main` regardless of how the command was spelled.
  It also already covers force-pushes to main, since it blocks all pushes
  there.
- **The real gap:** nothing canonical stops a force-push to a *topic* branch
  — the deny patterns are the only thing there, and they do not hold. Either
  extend `.githooks/pre-push` to refuse a non-fast-forward update on any ref
  (the remote sha is on stdin already, so `git merge-base --is-ancestor` is
  the whole check), or state in `CLAUDE.md` that this case is deliberately
  unprotected. Silently relying on the patterns is the one option that is
  wrong.
- `CLAUDE.md` already warns that `*` spans spaces (`Bash(git *)` allows
  `git push --force`). Extend that paragraph rather than starting a new one:
  the existing note is about rules being *too broad*; the new one is about
  rules being *evadable*, and the 141 allow rules installed on every machine
  are attack surface in the CVE-2026-22708 sense, not just convenience.
- Touchpoints: `claude/settings.json` (comment-free JSON — the explanation
  goes in `CLAUDE.md`), `CLAUDE.md` § "Claude Code config", `.githooks/pre-push`,
  and one line in `claude/agents/security-sweep.md`'s vetting criteria so a
  reviewed diff that adds a pattern-based guard is flagged as such.

**Done when:** `CLAUDE.md` names, for each thing the deny array protects, the
canonical control that holds when the pattern does not — and force-push to a
topic branch is either blocked by `.githooks/pre-push` (with a bats test, per
the "add a test when you add a guard" rule) or documented as knowingly out of
scope.

**Source:**
<https://adversa.ai/blog/opensource-ai-coding-agents-shell-injection-vulnerability/>,
<https://www.helpnetsecurity.com/2026/06/11/owasp-prompt-injection-ai-security-failures/>,
<https://code.claude.com/docs/en/changelog>

**Not already covered because:** `CLAUDE.md` documents two permission
pitfalls — `*` spanning spaces, and a leading `/` anchoring to the settings
directory — but both are about writing a rule that is *wider than intended*.
Neither says a correctly-written rule is bypassable by quoting, and no
decision in `PROJECT_STATUS.md` touches the deny array. The 2026-07-21
sandbox-first decision is adjacent and is the reason this is a documentation
and hook change rather than a settings rewrite: the sandbox, not the rule
list, is where containment lives.

### 2. Give `vibe loop` a spend ceiling alongside `--max` and `--for`

**Goal:** an unattended loop can be bounded by cost, not only by rounds and
wall-clock, so the weekly SOTA cron and any overnight `vibe loop` have a hard
gate on the one axis that currently has none.

Design:

- Keep it agent-agnostic. `VIBE_LOOP_PERMISSIVE_ARGS` is already the
  agent-specific escape hatch and was deliberately left empty (see the
  2026-07-21 reasoning on not hardcoding a Claude default). The cheapest
  correct version of this item is **documentation, not code**:
  `docs/vibe-loop.md` gains a recommended `VIBE_LOOP_PERMISSIVE_ARGS` value
  for Claude Code that includes `--max-budget-usd`, now that v2.1.217 makes
  the flag actually halt running background subagents rather than only deny
  new spawns.
- If a code change is wanted, the agent-agnostic shape is a new
  `VIBE_AGENT_BUDGET_ARGS` env var appended the same way
  `VIBE_AGENT_HEADLESS_ARGS` is, empty by default — *not* a `--budget` flag
  that `bin/vibe` would have to translate per agent.
- `docs/sota-watch.md` should say what the weekly cron's ceiling is, since
  that loop runs with nobody watching by design.
- Touchpoints: `docs/vibe-loop.md`, `docs/sota-watch.md`, optionally
  `bin/vibe` (the `argv` assembly near the `VIBE_AGENT_HEADLESS_ARGS`
  expansion) plus a bats case asserting the extra args reach the agent
  command line via `$VIBE_TEST_TMUX_LOG`.

**Done when:** `docs/vibe-loop.md` documents a spend ceiling as a first-class
part of configuring an unattended loop, on the same footing as `--max` and
`--for`, and `docs/sota-watch.md` states the ceiling the weekly run uses.

**Source:** <https://code.claude.com/docs/en/changelog>,
<https://www.requesty.ai/blog/loop-engineering-how-to-build-ai-agent-loops-that-run-themselves>

**Not already covered because:** `vibe loop` has three stop conditions today
— the `--until` stop check, `--max` rounds, and `--for` duration — and none
is a cost bound. The adjacent decision is the 2026-07-21 one declining to
hardcode Claude-specific defaults into `VIBE_LOOP_PERMISSIVE_ARGS`; this item
respects it by putting the Claude-specific flag in a doc example and keeping
any code change to a pass-through variable.
